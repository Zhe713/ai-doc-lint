# 面试 FAQ（基于本项目真实做法）

> 本文件整理 ai-doc-lint 项目的核心技术问题与真实答案，用于面试讲述。每个答案都对应仓库中可指认的代码/文档/数据，不是包装话术。

## 1. 这个项目解决什么问题？为什么有价值？

合同审查有两个现实痛点：一是格式、错别字、条款缺漏等机械性检查占用大量人工时间；二是人工逐份比对多份合同（主体、金额、日期一致性）容易漏。ai-doc-lint 把"机械校对"交给 AI/规则，把"实质性风险判断"留给人（法务/业务），产品口号就是"让 AI 做校对，行家做判断"。

**真实性支撑**：`README` 当前进度 W1-W8 全量；golden 基准集 40 份网络公开真实合同（CUAD 英文 + 政府采购中文 + 示范文本库），误报率从 391 收敛到 7。

## 2. 这是 RAG 项目吗？检索怎么做的？

是"规则引擎 + RAG"双通道。规则通道（格式/条款完整性/金额勾稽）**全部 0 token 本地运行**，可离线；RAG 通道负责语义检索与文档助手问答。

检索链路（`backend/app/services/bm25.py`、`reranker.py`、`api/search.py`）：

```
本地 bge-small-zh 嵌入（0 token）
  → pgvector 向量检索
  + BM25 关键词检索（混合）
  → bge-reranker 重排
  → 结果带原文引用返回
```

**为什么自托管**：合同是机密数据，BYOK（自带大模型 Key）模式保证数据不出部署方；本地嵌入模型保证核心能力零成本、可离线。

## 3. AI 幻觉怎么防？（高频追问）

四层防制，全部可指认：

1. **引用防幻觉**（`backend/app/services/`）：LLM 回答/抽取必须给出文档原文片段引用，前端可跳转定位，无引用不采信；
2. **规则预筛**（W3 意图漏斗 L1/L2）：先规则层穷举检查，LLM 只做规则层无法判定的补充，缩小幻觉影响面；
3. **人工闸门**（W2）：解析失败/低置信场景三选一（OCR 重试/带警告继续/取消），关键判断交给人；
4. **自学习闭环**（W7）：误报反馈（词典/规则过严/上下文/其他）回流 → 每日自动调优 → golden F1 回归验证，先验证再生效。

## 4. 自学习闭环怎么设计？（亮点）

五步（`backend/app/tasks/learning.py` + 报告页反馈采集）：

```
用户反馈（误报原因结构化）
  → 诊断看板（反馈分布、候选建议）
  → 自动调优任务（白名单扩充 + 停用建议）
  → golden 基准回归（40 份真实合同 F1）
  → 通过才生效，未通过挂起人工
```

关键设计：**先验证再生效**（DB 信号 + golden 两级验证），避免调优引入新误报。

## 5. 技术栈为什么这么选？

| 组件 | 选型 | 理由 |
|---|---|---|
| 后端 | FastAPI + SQLAlchemy + Alembic | 异步原生、类型安全、自动 OpenAPI 文档 |
| 前端 | Vue3 + TypeScript + Element Plus | 组件生态成熟、类型安全、构建含 vue-tsc 门禁 |
| 数据库 | PostgreSQL 18 + pgvector | 关系数据 + 向量检索一体化，避免引入 ES 等重组件 |
| 缓存/队列 | Valkey + Celery | 与 Redis 兼容、四队列隔离（parse/review/annotate/learn） |
| 对象存储 | MinIO | S3 兼容、自托管文件存储 |
| 嵌入/重排 | sentence-transformers 本地模型 | 0 token、离线可用 |
| 部署 | Docker Compose（7 容器）+ Nginx | 一键起、单机可跑、CI 同构 |

**权衡**：自托管整套（含向量库/对象存储）换来了"数据不出域"，代价是运维复杂度，用 Docker 编排抵消。

## 6. 异步任务体系怎么设计？

Celery 四队列 + Beat 定时巡检（`backend/app/tasks/`）：

- 批量上传 100 份受理、sha256 去重、在途配额；
- 解析流水线：txt/md 直解 → pdfium 文本探测 → docling 结构化抽取 → 扫描件 RapidOCR 兜底（离线可用）；
- 卡死任务巡检 + 断电恢复（reaper）；
- 数据保留自动清理（每日 04:30）。

## 7. 误报率 391 → 7 是怎么收敛的？

1. **真实数据驱动**：golden 集用网络公开真实合同（禁自造文件），建立可复现基准；
2. **混淆集校准**：错别字检查器用混淆集（合法用法 / 常见误用）校准，删损坏行、加注释；
3. **规则回归**：每次规则调整跑 golden F1，白名单先验证再生效；
4. **结果量化**：L3 指标（上传即拦截率、每份发现问题数、严重度分布）跟踪业务价值。

## 8. 测试与质量怎么保证？

- 后端 pytest **163+ 用例全绿**，CI 双 job（后端测试 + 覆盖率门禁 ≥70%；前端 vue-tsc 构建）；
- 覆盖率实测 **71%**（含任务/工具类大量边界代码）；
- GitHub Actions + Dependabot + CodeQL 自动更新与安全扫描；
- 安全基线：Nginx 安全响应头（CSP/nosniff）、上传 MIME 魔数校验、审计日志、密钥仅环境变量。

## 9. 你踩过的最大的坑？

（按个人经历讲其一即可，下面给三个真实案例）

- **中文文件名导出 500**：API 下载响应头 `filename*` 需 UTF-8 编码，直接 `filename=` 传中文在部分浏览器/库会崩——改为 RFC 5987 规范后修复（`backend/app/api/`）；
- **规则包污染测试断言**：测试库与主库共享规则加载，自定义包导致 `rule_id` 断言漂移——加 autouse fixture 把规则加载会话隔离到测试库；
- **扫描件无文字层**：用户上传损坏/纯扫描 PDF 直接解析失败且无指引——改成"交互式解决"（OCR 重试/带警告继续/取消 + 向导文案）。
