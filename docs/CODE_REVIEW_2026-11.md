## 一、一句话结论

核心能力是**真的**，不是演示壳子；但"最后一公里"的信任设计很差——用户看到的结论，
和系统实际做了什么，中间经常对不上。这类问题比功能缺失更致命，因为它会让人**误以为审过了**。

---

## 二、实测：核心链路到底能不能跑

用真实合同走完整流水线（登录 → 上传 → 解析 → 四类检查 → 报告 → 导出 → 批注）：

| 环节 | 实测结果 | 判定 |
|---|---|---|
| 上传 / 去重 | 201，重复文件按 sha256 跳过并回传清单 | 真 |
| 解析 | txt / docx 均成功，任务状态流转正常 | 真 |
| 勾稽检查 | 检出"单价 1,200×100=120,000 与总价 130,000 不一致" | 真 |
| 格式检查 | docx 检出 5 条字体不合规 + 1 条首行缩进 | 真 |
| 意见书 PDF | 1 页 289 字，含结论/风险分布/问题清单/建议 | 真 |
| 摘要 JSON | 含结论与放行建议（前端未使用） | 真但闲置 |
| Excel 明细 | 2 个工作表、13 个单元格、含审查汇总 | 真 |
| 批注（docx） | 生成 **6 条 Word 原生批注**（comments.xml），带修订锚点 | 真 |
| 批注（txt） | 在问题位置插入【AI批注·error】+ 建议 | 真 |
| 交叉比对 | 建组→矩阵→比对发现→导出 CSV，链路完整 | 真 |

**结论：主干是实的。** 这一点要先说清楚——它不是"看起来有功能"，是真能出东西。

## 三、逻辑缺陷：实测确认的真 bug

### 已修复（本次改动）

1. **"没检查"被显示成"没问题"（最严重）**
   选"招投标/制度/报告"类型 + 勾选条款检查时，条款包不存在，检查器直接 skip，
   报告仍显示"0 问题 / 已完成"。实测：招标文件跑完 `total=0`，而 `skipped` 里明确有
   `clause.check`、`cross_rules`。
   修复：`GET /documents/{id}/findings` 现在返回 `checks_skipped`（含"整类未执行"标记），
   报告页用橙色横幅明示"条款完整性、数值勾稽未执行，本报告不是完整审查结论"。

2. **检查器降级警示永远不触发**
   `checker_warnings` 写在 review 任务，代码却从 parse 任务读。实测量：review.stats 里
   有降级说明，接口返回 `checker_degraded: false`。已改为从 review 任务读，并按实际内容显示文案。

3. **"确认有效"把状态写回 open**
   用户点"确认有效"，提示"已记录，谢谢反馈"，但结果仍计入待处理，看起来像没生效。
   语义正确但文案误导，已改为"已确认为真实问题；改完合同后请点「标记已修复」"。

4. **规则包跨用户污染（安全问题）**
   `RulePack` 有 `user_id`，加载时却完全不看：任何一个普通用户存一个规则包，
   **全系统所有人**的审查规则都会被替换。
   已改为按创建者隔离，并补测试锁住该契约。

5. **空规则包能存进库**
   前端用 `json.includes('"clauses": [')` 判空，而空数组同样包含该子串，校验形同虚设。
   已改为解析 JSON 后判断数组长度。

6. **"新增 / 修改规则"里的"修改"是假入口**
   页面标题写着修改，但 `updateRulePack` 全仓库零调用、`onCopyBuiltin` 是死函数。
   已补"编辑"按钮：回填表单 → 保存覆盖原包（类型锁定，避免与后端契约冲突）。

7. **"看说明"点了没反应**（你截图指出的那个）
   函数会加载说明，但**没有切换页签**，用户停在"我的规则包"看起来什么都没发生。
   已改为自动跳到"① 看规则"。

8. **全站大面积静默失败**
   报告页状态变更/导出、搜索、版本对比、交叉比对、规则启停、系统设置——大量
   `try/finally` 无 `catch`，失败时用户零反馈。
   已改为**在 axios 响应拦截器统一兜底**：提取后端 `detail`、区分超时/网络/403/429/5xx，
   同一提示 4 秒内去重（防止轮询刷屏）。这是治本做法，不是逐页补 catch。

9. **被去重跳过的文件被静默吞掉**
   后端返回 `duplicates`，前端类型里没这个字段。用户只知道"少了几份"，不知道少了哪些。
   已补类型并提示具体文件名。

10. **审查未完成时先给结论**
    parse 完成后 review 才入队，中间有几秒空窗；前端轮询只看 group 内是否还有 running，
    空窗期会停止轮询并显示 0 问题。
    已新增 `review_pending` 标志，报告页据此自动续等（上限 90 秒）并提示"结果可能不完整"。

### 未修复（需要你决策，见第五节）

- 每日智能审查限额：有 UI、有存储，**全仓库无任何消费点**，纯装饰。
- 内置规则"确认停用"实际未停用，列表却显示"已停用"（学习闭环的假闭环）。
- 「自动放行」只是布尔徽标，不落库、不改状态。
- 用户管理页面只有只读表格，无停用/改密/改角色。
- 字段抽取（金额/日期/当事人）前端完全未展示，只在比对矩阵里露脸。
- 建比对组时会双跑（后端建组已自动入队，前端又触发一次）。

## 四、用户会不会真的用

分人群判断，不给你一个含糊的"能"。

| 人群 | 会不会用 | 原因 |
|---|---|---|
| 技术型自部署用户（你自己/开源尝鲜者） | **会用** | 一条命令起服务、BYOK、数据不出内网，这是真卖点 |
| 中小企业法务 | **会用一半就放弃** | 报告结论看不懂（`clause.payment_term` 这种机器码直接当标题）、无法判断 AI 依据是否可信 |
| 商务/采购（最常见目标用户） | **不会用** | 术语门槛高；出错无提示；不知道"该看哪一条" |
| 律所/大企业 | **不会用** | 无协作、无版本留痕、无批量、无审批流 |

**关键判断**：产品价值成立（合同审查确实痛、确实费人），但现在的形态是
"**给工程师看的合同审查工具**"，不是"给法务用的"。差距不在算法，在三处：

1. **结论的可信度无法验证**——用户没法从界面上确认"AI 是不是真的看了这段"。
2. **失败不可见**——查不出来、没查、查错，三种情况长得一模一样（本次修掉了最严重的一半）。
3. **术语没有翻译**——rule_id、checker、source 这些词直接暴露在业务界面上。

换句话说：**功能完成度 70%，产品完成度 35%。**

## 五、架构层面的问题（比单个 bug 更值得改）

1. **前后端契约靠手写，已经在漂移**
   实测到 3 处：`UploadResult` 缺 `duplicates`、`CompareGroupDetail` 缺 `field_labels`、
   `docs` 类型缺 `created_at/size_bytes`。
   建议：由 OpenAPI 自动生成 TS 类型（`openapi-typescript`），CI 里 diff 报警。
   现在的 `npm run build` 只跑 `vite build`，**不做类型检查**，这类错误会持续累积。

2. **任务编排有空窗**
   `parse → 入队 review` 是两段式，中间状态对外不可见，导致上面第 10 条。
   建议：合并为单一 review 流程，或给任务组一个显式状态机（`parsing → reviewing → done`），
   前端只认这个状态。

3. **能力边界没有一等公民地位**
   `skipped` / `checker_warnings` 只是 stats 里的附带字段，没有任何 schema，
   消费方各自猜。建议正式建模为 `Coverage`（哪些检查执行了、哪些没有、为什么），
   贯穿 API、报告、导出。

4. **规则包的定位模糊**
   既像"管理员全局配置"（旧行为），又带 `user_id`（新行为）。本次已统一为"用户私有"。
   若要支持团队共享，应显式引入 `scope`（personal / team / global），而不是靠"谁最后保存"。

5. **前端零测试 + 类型不设防**
   后端 169 个用例很扎实，前端一个测试都没有，且构建不校验类型。
   建议：先修 tsconfig（TS6310 那个基线问题），再开 `vue-tsc --noEmit`，最后补 3~5 个关键路径测试。

## 七、如果只做三件事

1. **把"未执行/降级/失败"做成第一等公民**——已完成一部分，剩导出文件里的结论页也要标注。
2. **把 rule_id 全量翻译成人话**（条款名称、检查项名称），这是门槛最低、收益最大的一步。
3. **修好 4 个假闭环**（限额、内置规则停用、自动放行、用户管理），或者干脆把入口删掉。
   半成品比没有更伤信任——用户试一次发现是假的，就不会再信第二个功能。
